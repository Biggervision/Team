Automating WordPress
without getting blocked

Everything that cost us time on the Evergreen OC build, written down so the next site doesn't repeat it. Applies to any tool hitting the WordPress REST API — Claude Code, a script, a scraper.

The one rule

Never send a browser User-Agent. Say what your software actually is. Hosting firewalls block outdated browser strings on sight, because that is what malicious traffic pretends to be. One wrong header cost us most of a working day and got an entire IP range greylisted.

✅  EvergreenOC-ContentSync/1.0 (WordPress REST client; +https://site.com)
❌  Mozilla/5.0 (Macintosh...) Chrome/126.0.0.0 Safari/537.36

Before you start

  1. Create an Application Password (Users → Profile), not the login password. Revocable in one click, and it can't be used to sign in.
  2. Set a descriptive User-Agent with a contact URL. See the rule above.
  3. Tell the host before you start a bulk job. A heads-up costs a support ticket; being greylisted mid-run costs a day.
  4. Check what the database charset is if content contains emoji. See #5.
  5. Back up every record before you write to it. One JSON file per post, kept in the repo, makes any mistake a one-line revert.

What will bite you

01

The block is invisible in the host's logs

Symptom
Requests return HTTP 202 with a tiny HTML body that meta-refreshes to a captcha URL. Support says “we see normal 200 OK responses, your IP isn't blocked.”
Cause
The challenge is served by the edge firewall, in front of PHP. WordPress never receives the request, so it never appears in the site's access log.
Fix
Send support the response headers, not a description. The giveaway header names the security layer directly:
HTTP/2 202
sg-captcha: challenge          ← this is the proof
server: nginx
02

Your IP rotates, so one allowlist entry is useless

Symptom
Host allowlists the IP you sent; you're still blocked.
Cause
Cloud tooling egresses from a pool. We saw eight different addresses in under a minute.
Fix
Sample it 20–30 times, then give the host the whole range. curl -s https://api.ipify.org in a loop. Better still, fix the User-Agent so no allowlist is needed at all.
03

Retrying harder makes it permanent

Symptom
A job that was half-working stops working entirely, and stays broken for hours.
Cause
Aggressive retry loops are exactly the pattern a firewall greylists. Running two jobs at once doubles it.
Fix
One job at a time. Back off in minutes, not milliseconds. If success rate drops toward zero, stop — continuing renews the timer rather than getting through.
04

Elementor caches separately from the host

Symptom
You edit a template, the change saves, and the page still shows the old version — even on URLs never visited before. Looks exactly like a failed save.
Cause
Elementor caches rendered output independently. Purging the host cache does nothing for it.
Fix
Clear Elementor first, then the host. Note the method — POST to that purge route returns a confusing 404.
DELETE /wp-json/elementor/v1/cache            ← this one matters
PUT    /wp-json/siteground-optimizer/v1/purge-cache   ← PUT, not POST

Before assuming a write failed, read the value back over the API. It is almost always cached, not broken.

05

Emoji silently break database writes

Symptom
HTTP 500 rest_meta_database_error — “Could not update the meta value of X in database.” Only some records fail.
Cause
The table is 3-byte utf8, which cannot store 4-byte characters. Any emoji in the content kills the write.
Fix
Encode astral characters as HTML entities before writing. They still render correctly, and store as plain ASCII.
"".join(c if ord(c) <= 0xFFFF else f"&#x{ord(c):X};" for c in text)
06

Custom field plugins hide their data from the API

Symptom
meta comes back null, and posting a meta payload is rejected outright.
Cause
Fields aren't registered for REST. With JetEngine, the show_in_rest flag isn't in the field schema and isn't in the UI — but the plugin honours it if you write it in anyway.
Fix
Set it on the post type definition, then re-read one post to confirm before touching the rest. Any field added later needs the same flag or it silently won't save.
07

An open wp-admin tab will wipe your work

Symptom
Content written via the API reverts to its old state with no error anywhere.
Cause
An edit screen opened before the API write, then saved, submits the stale form it loaded with — overwriting everything.
Fix
Close or reload wp-admin tabs before running a job, and again before saving anything by hand afterwards. If content reverts, check the modified timestamp — it names the culprit.
08

Custom post types swallow a whole URL path

Symptom
Existing pages under /thing/ start returning 404 the moment a custom post type is registered with that rewrite slug.
Cause
The post type claims the entire path. Old pages still exist in wp-admin but have no working URL.
Fix
If old and new share a slug, the URL is unchanged — publish, don't redirect. A 301 there would intercept the URL before the new post could serve it and point it at itself. Only genuinely orphaned URLs need redirects.
09

Draft posts are 404s, and internal links to them are dead

Symptom
A link audit passes — every link present, correct, pointing somewhere real — yet the links don't work.
Cause
The targets are unpublished. The link is right; the page isn't there yet.
Fix
Audit two things separately: is the link correct, and would it load for a visitor. Publishing is the fix, not a redirect.
10

“It's there” is not “you can see it”

Symptom
Links verified present and resolving, but invisible on the page — the client finds them by browsing, not the audit.
Cause
The theme styled paragraphs and bold text but never anchors, so links inherited body colour with no underline.
Fix
After any content job, look at the rendered page. Automated checks confirm data, not design. Also check contrast — a brand green that works on a dark band can be unreadable on a cream one.
11

Grep the content for developer notes before publishing

Symptom
A field reading TODO(Pro): confirm live price rendered publicly on 89 pages the moment they were published.
Cause
Placeholders left by whoever built the template. They were harmless while everything was a draft.
Fix
Before publishing, scan every field for TODO FIXME XXX TBD PLACEHOLDER LOREM WIP. Treat a TODO as a real task: resolve it, or remove the note — don't leave it standing.
12

Every host's firewall has different rules

Symptom
The header that fixes one site breaks another.
Cause
On this project SiteGround challenged browser user-agents, while the Weedmaps storefront did the exact opposite — returning 406 to browser strings and serving requests with no UA normally.
Fix
Test each host with a handful of requests before assuming. Document what worked, per host, in the repo.

Working with hosting support

  • Lead with evidence. Response headers, exact status codes, timestamps and the full IP range. “It's blocked” gets “our logs look fine.”
  • Ask which layer. WordPress, .htaccess, or the edge firewall? Different teams, different fixes.
  • Don't ask them to switch off security rules. If support offers, decline. On this project the rules were right and our header was wrong — the fix belonged on our side.
  • Ask for delisting, not just allowlisting. Existing greylist entries persist after an allowlist is added, and will keep challenging you until they're cleared or expire.
